Machine Time

Work in machine time. Sign in human time.

Human time is serial: one person, one pair of hands, and the work queues up behind them. Machine time is parallel: agents run side by side, so hundreds of machine hours fit inside a single wall-clock day.

The work did not get faster. It changed clocks. In theory a new product can now be brute-forced into existence in days, and some days it nearly is. What decides whether that speed turns into something worth shipping is where the human hours go.

Limits

Three things cap machine time

Machine time feels unlimited until you run it, price it, and try to stand behind what it makes.

Concurrency

How many agents run at once. Every added lane is another stream of work inside the same wall-clock hour, bounded by how many streams one person can direct well.

Cost

What the machine hours cost. Agents are cheap, and they run in parallel. The bill is not the constraint it used to be. Cheap is not free, though: you can burn credits solving the wrong problem, and it happens all the time. The spend is small. The wasted direction is not.

Verification bandwidth

How much machine output one accountable person can check and sign for. Generation scales with money. Trust does not. This is the ceiling that decides how much machine time is actually usable.

Economics

The economics flipped

Skilled human hours used to be the input everything else waited on, so they were rationed: fewer attempts, bigger plans, long arguments before anyone wrote a line. Agent hours invert the rationing. Generation is cheap, parallel, and always on, so the strategy flips with it: run several approaches at once, keep the best, and kill wrong directions while they are still cheap.

One more try

The cost of another attempt, another draft, another approach: close to nothing next to the human hour it once took.

Every lane at once

Machine hours scale sideways. Buy more lanes and the same day holds more work. The calendar stops being the budget.

One signature

The input that never gets cheaper and never parallelizes: one accountable person for every change that ships.

The scarce inputs now sit at the ends of the pipeline: a clear intent, the judgment to tell good from almost good, and a person willing to sign. The expensive failure is no longer slow production; it is fast production of the wrong thing, shipped before anybody checked. Machine time is bought by the hour. Human time is spent on what matters.

Workflow

The machine-time workflow

The method as steps, in the order I run them. Anyone can run this. The steps are not the secret; running them every time is.

  1. Write the intent. In human time, write what the work is for and what done looks like: the intent and the acceptance criteria. This is the part agents cannot supply.
  2. Generate in parallel. Run agents in machine time, side by side, and let them produce the work against that intent.
  3. Pass the gates. Deterministic checks first: the build, the tests, static analysis. They pass the work or they stop it. No warnings that everyone learns to ignore.
  4. Get a fresh-context review. An AI reviewer that did not write the code reads the diff against the intent and flags what does not fit.
  5. Verify and sign. A person checks the output, spot-checks the risky paths, and signs off on the risk. The signature is the step that does not scale, and it is not supposed to.
  6. Ship small, with an exit. Release in small increments behind flags, with a rollback path ready for whatever slips through.

Verification

Reviewing at machine time: the human in the loop

Generation is not the bottleneck any more. Review is. Reading every line does not scale, and rubber-stamping is not review. What scales is a process: the work arrives with evidence, machines decide what machines can decide, and the human spends attention where the risk actually is.

  1. Demand the receipts first. No review starts until the change arrives with its evidence: the intent it was built against, the acceptance criteria, a plain summary of what changed and why, and the build and test output. Missing receipts end the review before it starts. Send it back.
  2. Let machines take the first pass. Build, tests, static analysis, and security scans run automatically and block on failure. They are gates, not warnings. A human should never spend attention on a question a machine can settle.
  3. Get an independent AI review. A reviewer with fresh context, one that did not write the code, reads the diff against the intent. Its job is mismatch hunting: behavior nobody asked for, edge cases nobody handled, tests that pass without testing anything.
  4. Review in a fixed order. Intent first: is this the right thing, built the way the intent described? Then the risky paths, line by line. Then the tests: do they actually prove the claim, and did anything weaken them to get a pass? The generator never edits its own tests. Spot-check the rest, and do not pretend a skim is a read.
  5. Sign one change, by name. An approval covers one specific change and belongs to a person. An agent's approval never counts as a person's. If you would not put your name on the failure, it does not ship.
  6. Ship contained, then close the loop. Flags, staged rollout, monitoring, and a rollback path are the last layer of review, because some defects only show up in production. Every miss that gets through becomes a test, a gate, or a checklist item, so next time the process catches it instead of luck.

That is the whole trick to moving at machine time with a human in the loop. The machine produces the volume. The process decides where the human looks. The signature decides what ships.
